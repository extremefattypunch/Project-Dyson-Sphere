## A. Summary

- **Link budget** (`link_budget.py`, PDF §10.1/§10.4). `evaluate_link_budget` returns a
  `LinkBudgetResult` with every stage power (`P_PV`, `P_PV,tx`, `P_dc_to_tx`, `P_beam`,
  `P_aperture`, `P_atm`, `P_captured`, `P_accepted`, `P_receiver`, `P_grid`) and every efficiency
  per epoch, plus the PDF p.4 names (`power_at_transmitter_W`, `power_at_receiver_W`,
  `atmospheric_factor`, `rx_electric_W`, `grid_W`). One owner per factor: the on-board stages
  come only from `power_chain.onboard_power_chain` (spy-tested), `η_capture` is
  `BeamResult.capture_fraction` (pattern normalised to `P_aperture`; taper, wavefront/Ruze,
  lattice and pointing already inside, no extra aperture efficiency), `η_atm` from M5.
  Invariants (every η ∈ [0, 1]; no passive stage increases power; `P_grid = 0` when not
  transmitting) are checked exactly on construction and raise `LinkBudgetInvariantError`.
  Receiver constraints are part of the chain: input limit on `P_captured` (M0 definition) and
  heat-rejection limit `P_accepted ≤ Q_max/(1−η_rx)` clip and flag `RECEIVER_SATURATION`;
  `max_power_density_W_m2` is a **beam abort** (the only policy the schema defines) evaluated
  on the aberration-free peak irradiance `P_atm·I_peak/W`.
- **System run** (`system.py`). `run_single_satellite(config, *, ephemeris, kernels, rng,
  earth_orientation=None, backend="numpy") -> SystemRunResult` runs orbit (L1 or L0) →
  illumination → solar/PV/thermal/ledger (M4) → retarded-time access and occultation (M3) →
  atmosphere and beam capture with pointing statistics (M5) on the epochs with access →
  availability conditions → link budget, all vectorised over the output grid. A `uint32`
  `Unavailability` bitmask per epoch (10 blocking reasons: elevation, Earth/Sun/Moon
  occultation, Sun avoidance, eclipse, thermal, weather, pointing, power-density abort; 2
  limiting flags: receiver saturation, partial eclipse); `P_grid = 0` exactly where any blocking
  bit is set. Thermal infeasibility stops the transmitter (no derating policy exists in the
  schema). Only one receiver site is accepted (several need the M7 scheduler). The run is
  deterministic; the explicit Generator is recorded as unused (no stochastic step).
- **Metrics** (`metrics.py`), computed from the saved `timeseries.parquet`: P_grid time mean
  (trapezoid), median/p05/p95/peak, mean when available, delivered energy, availability
  (time-weighted), capacity factor with a defined rated power (`ReferenceLink`: window-mean
  heliocentric distance and range, zenith, clear sky, configured pointing, receiver limits),
  outage count/duration distribution/longest (±1 step, censored ends flagged), end-to-end
  efficiency `E_grid/E_incident`, stage energies, capture and power-density statistics,
  unavailability breakdown (flagged and primary fractions) and the **diurnal-aliasing
  diagnostic** (largest hour-angle gap, effective distinct diurnal phases, warning).
- **Run outputs** (`io.py`, `manifest.py`): run directory with `config_resolved.yaml`,
  `manifest.json` (config hash, schema version, git commit + dirty flag, Python/package versions,
  OS, CPU, host, Slurm ids, JAX devices, seed and generator use, kernel names/URLs/SHA-256,
  ITU-R versions and polarisation tilt, time-scale and frame notes, wall-clock start/end, stage
  wall times), `timeseries.parquet` (73 columns, units in names), `summary.json`, `figures/`,
  `report.md`, `logs/run.log`. Refuses to overwrite without `--overwrite`, and even then only
  replaces a recognisable helioswarm output directory. `summary.json` and the time-series
  content hash are bitwise reproducible (tested).
- **Figures and report** (`plotting.py`, `report.py`) are drawn only from the saved files
  (tested by deleting them and running `helioswarm plot` with the model functions patched to
  raise): orbit/range/elevation, solar/thermal, beam capture/pointing/Fresnel number, stage
  waterfall + `P_grid(t)`, unavailability, composite page; the one-page report lists key
  parameters with provenance labels, the metrics table, provenance and figure links.
- **CLI**: `run`, `plot`, `sweep` (Cartesian grid over dotted keys, `--summary-only`,
  `--array-index/--array-count`, resumable, `--collate-only`, failures recorded) and
  `validate-models --report` (31 programmatic checks, generated block in the report).
- **Configs**: `mvp_single_satellite_microwave.yaml` (2.45 GHz, 1 km phased array, 10 km
  rectenna, ITU-R atmosphere; every value labelled assumed), `optical_1au_sweep.yaml`
  (5 radii × 3 apertures × 3 receiver radii = 45 points) and the aliasing-validation run
  `mvp_single_satellite_step3896s.yaml` (3896 s step, day-incommensurate). The MVP optical
  config is unchanged (PDF values; true anomaly 30° → satellite ~70° behind the Earth, range
  1.122–1.180 au, reported).
- **Slurm** (`slurm/`): `run.sbatch`, `sweep_array.sbatch`, `validate_models.sbatch`,
  `gpu_bench.sbatch`, `profile.sbatch` and the shared `common.sh` (`#!/bin/bash -l`, netscratch
  logs, `scripts/cluster_env.sh`, `uv run --locked`, node-local `TMPDIR` with trap cleanup,
  outputs in `$HELIOSWARM_RUNS_DIR`), sized from measurements.
- **Optional GPU backend** (`capture_batch.py`, extras `jax`/`gpu`): the Airy capture
  expectation for many independent points as one array program (numpy or JAX). It agrees with
  the M5 reference to 5e-12 and JAX with numpy to 3e-16 (CPU and A100 GPU). Measured on
  `gpu_test`: 11.8× faster than the vectorised numpy batch and ~106× faster than the per-point
  reference at 1e5 points; but profiling shows the beam stage is 7.6 % of an MVP run and the
  serial L1 orbit integration 85.6 %, and in the sweep the beam time is spent in capture
  percentiles that the kernel leaves on the CPU, so **no production job requests a GPU**; the
  path stays optional and off by default.

Negative results, stated plainly:

- **Optical MVP (PDF example design): 1.75 kW mean delivered from 3.67 MW of PV**, an
  end-to-end efficiency of 1.3e-4. The beam (10 m aperture, 1 µm, ~1.15 au) has its first null
  at ~21 km; a 1 km receiver captures < 1 % of it. Diffraction, not geometry or the
  atmosphere, dominates the loss.
- **Microwave MVP: 0.31 W mean** (capture ~4e-7) even with a 1 km phased array and a 10 km
  rectenna; microwave power beaming from ~1 au is negligible.
- **Hourly sampling biases availability by −0.0195 absolute (−4.4 % relative)**: 0.4221 at
  3600 s vs 0.4416 at the day-incommensurate 3896 s step (whose gap is 0.26°, resolution 7e-4
  of a day); delivered energy −1.2 % (15.35 vs 15.54 MWh), mean P_grid −1.2 %. The MVP keeps
  the PDF's 3600 s step; its summary carries the warning.

the device passed. Percentiles add a per-point CPU fallback where η(d) is non-monotone (200 of
1000 points here; 18.0 s for 1000 points with percentiles on the CPU).

Decision (PDF §14.3): the kernel is ~12× faster on a GPU slice than vectorised numpy, but it is
only 7.6 % of a run (the serial orbit integration is 85.6 %), so a GPU would shorten a run by at
most ~8 %. In the benchmark job itself the GPU was busy only during the JAX calls (≈ 95 s of a
407 s job, < 25 %), and `jobstats` cannot report MIG utilisation. Therefore no run, sweep or
validation job requests a GPU; `--backend jax` stays optional and off by default. It becomes
worthwhile only for workloads dominated by capture *expectations* over ≳1e5 points (e.g. a
future pointing/geometry Monte Carlo on fixed trajectories). In the 45-point sweep the beam
stage did dominate (mean 54.5 s vs 31.7 s for the orbit per point), but that time is the
level-set capture *percentiles* for receivers beyond the first Airy ring, which the batched
kernel hands back to the CPU reference (the benchmark's 1000-point batch: 2.0 s for the numpy
expectation, 0.52 s on the GPU, 18.0 s with percentiles on the CPU); a GPU would not have
shortened the sweep materially.

## E. Assumptions and equations implemented

Full text in `docs/model_assumptions.md`, "M6"; provenance in `docs/data_provenance.md`.

- **Stage chain** (PDF §10.1): `P_PV,tx = P_PV·1[tx]`, `P_dc_to_tx = P_PV,tx η_pc`,
  `P_beam = P_dc_to_tx η_e2b`, `P_aperture = P_beam η_o`, `P_atm = P_aperture η_atm`,
  `P_captured = P_atm η_capture`, `P_accepted = min(P_captured, P_max_in, Q_max/(1−η_rx))`,
  `P_receiver = P_accepted η_rx`, `P_grid = P_receiver η_grid`; `Q_rx = P_accepted − P_receiver`.
- **Beam abort** (PDF §10.4): transmit only if `P_atm · I_peak/W ≤ max_power_density_W_m2`,
  `I_peak/W = πD²/(4λ²R²)` for the Airy pattern (taper-reduced for tapered apertures; M5).
- **Availability** (PDF §10.4/§10.5): no blocking reason; `availability = Σ_avail w_k / T`.
- **Energy and mean power**: trapezoid weights `w_k` (Δt inside, Δt/2 at the ends),
  `E = Σ w_k P_grid,k`, `⟨P⟩ = E/T`.
- **Capacity factor**: `⟨P_grid⟩ / P_grid(reference link)` (definition in A and in every
  summary.json).
- **End-to-end efficiency**: `E_grid / E_incident`.
- **Aliasing diagnostic**: `g = max circular gap of the sampled hour angles`, phases `2π/g`,
  warning if `g/2π > 0.005`.
- **Batched kernel**: `η(d) = EE(k max(a−d,0)) + ∫ (k²/π)(J1(kρ)/(kρ))² 2φ ρ dρ`,
  `E[η] = ∫ η f_Rice`; JAX Bessel functions `J0 = ⟨cos(x sin τ)⟩`, `J1 = ⟨sin τ sin(x sin τ)⟩`
  over N = 4M trapezoid nodes.

## F. Known limitations and next milestone

### Deviations from the plan / task text, and why

1. **New config field `transmitter.min_pointing_efficiency`.** The task lists "pointing" as an
   unavailability reason, but the schema had no pointing condition; a defaulted optional field
   (None = not enforced) was added rather than an unconfigurable hard-coded threshold. The hash
   was re-pinned with the history recorded.
2. **Power-density policy is beam abort only.** The schema defines the field as a beam-abort
   constraint; no throttling option exists, so none was invented.
3. **Heat-rejection limit enforced as a clip**, flagged with the input limit as
   `RECEIVER_SATURATION` (the M0 field defined the bound but not the policy).
4. **Extra modules** `sweep.py`, `validation.py` and `capture_batch.py` (plan layout listed
   `validation.py`; `sweep.py` keeps the CLI thin; `capture_batch.py` is the optional backend).
5. **`slurm/profile.sbatch` and `slurm/common.sh`** in addition to the four requested templates.
6. **Sweep array on `test` uses 5 tasks**, not 9: the test QOS allows 5 submitted jobs per user
   (first submission rejected with `QOSMaxSubmitJobPerUserLimit`). The first 5-task array lost
   4 tasks to a race on `sweep_definition.yaml` (same temporary name in every task); fixed
   (private temporary + atomic `os.link`; tested with 16 concurrent creators) and the sweep was
   made resumable, then resubmitted.
7. **`validate-models` keeps the curated report.** It writes its generated block between
   markers in `docs/validation_report.md` instead of replacing the per-milestone record.
8. **Backend flag is a CLI option, not a config field**: it selects numerics, not physics,
   and must not change the configuration hash.
9. **GPU benchmark run before code freeze**: job 60108172 ran on an earlier M6 working tree;
   the kernel code it measured is unchanged since (only the percentile flag and the sweep
   fixes changed afterwards).

### Limitations

- Single receiver site; no scheduling or capacity sharing (M7).
- Weather is a deterministic scenario over the whole window; no cloud statistics.
- Thermal state evaluated at the full operating point; off-state and thermal inertia not
  modelled. In sizing mode the radiator margin is 0 by construction, so the reported binding
  margin minimum is 0 K (M4 deviation 5).
- Percentiles in the batched kernel fall back to the per-point CPU reference where η(d) is
  non-monotone; the level-set percentiles cost ~55–90 ms per epoch for receivers beyond the first
  Airy ring (90 ms measured for one D = 30 m, 7 km case; 55 ms average over the sweep's beam
  stage), which dominates the run time of large-receiver sweep points (up to 205 s of beam time
  per point). Vectorising the level-set percentiles is the obvious next optimisation; the GPU
  kernel does not help there because it delegates exactly those points to the CPU.
- The capacity-factor reference uses window means; it is a normalisation, not a nameplate.
- The hourly MVP step aliases with the diurnal cycle (quantified above; warning recorded).
- ITU-R production revisions (P.676-12) remain regression-pinned only (M5 open item); `itur`
  logs a spurious elevation warning at exactly 90° used by the reference link (recorded, not
  suppressed, in `AtmosphereResult.notes`).

### Next milestone

M7 (not authorised): constellation, receiver scheduling and capacity, built on
`run_single_satellite` per satellite with the receiver-limit stage moved into a deterministic
scheduler that prevents double counting.
